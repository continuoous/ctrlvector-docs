# Plan the implementation

!!! warning "Page status: Draft"
    This discovery method requires product-owner and implementation-lead review before validation.

## Start with the comparison question

Write the decision you want CtrlVector to explain in one sentence. A useful statement names:

- the result being explained;
- the reference and current Version–Period combinations;
- the dimensions at which users need to investigate the change;
- the business drivers expected to explain it.

Example: “Explain the Quarter-over-Quarter change in Freight Spend for Actuals by Country, Product, Mode of Transport, and controllable cost drivers.”

## Design from the decisions backward

Do not begin by reproducing the fields that analysts already collect. Begin with the decisions accountable leaders need to make and the explanations they would consider actionable.

For each proposed outcome, ask:

1. What decision should this result support?
2. What movement would cause leadership to intervene?
3. Which headwinds, tailwinds, offsets, and execution levers must remain distinguishable?
4. Which explanation would be technically correct but too aggregated to act upon?
5. Who can influence each driver, and who is accountable for reviewing it?
6. What evidence must survive into approval and the final story behind the numbers?

Evaluate every proposed Factor using three tests:

| Test | Question |
| --- | --- |
| Strategic relevance | Does the Factor explain a material decision, risk, opportunity, or target? |
| Mathematical sufficiency | Do the Factors and formulas reconcile the required outcome without gaps or double-counting? |
| Operational feasibility | Can the organization source, own, approve, and refresh the Factor at the proposed grain? |

A Factor that fails strategic relevance should not be added merely because data is available. A strategically desirable Factor that fails operational feasibility should be recorded as a gap, proxy, or later implementation wave rather than silently invented.

## Establish the independent financial contract

Where the implementation reconciles to a financial statement or governed KPI hierarchy, define the expected Node totals independently before manufacturing detailed Factor data.

```text
Published or approved statement
→ expected Node totals
→ Node hierarchy and formulas
→ Factors and natural grains
→ detailed values
→ bottom-up calculated totals
→ independent verification
```

The governing principle is:

> Top-down outcome contract; bottom-up operational proof.

Expected totals must not be regenerated by the same process that creates the detailed Factor values. Otherwise the final verification only proves that one calculation agrees with itself.

## Separate logical design from configuration order

The semantic model is designed before its objects are entered into CtrlVector. Use this logical sequence:

1. Define expected outcome totals and reporting bases.
2. Define the reusable Node hierarchy and formula contract.
3. Extract the required source and derived Factors.
4. Co-design candidate Dimensions with Factor natural grains.
5. Freeze Dimension members and reusable Dimension Policy patterns.
6. Define the intended business events, mitigations, and approval exceptions.
7. Create detailed input values at each input Factor's natural grain.
8. Calculate and retain expected impacts independently.

The physical CtrlVector configuration sequence is different because Dimensions and policies must exist before they can be assigned to Factors, and Factors must exist before Nodes reference them. [Configure the semantic model](semantic-model.md) describes that execution order.

## Resolve the Factor–Dimension design loop

Factors determine which business axes matter, while Dimensions determine how Factor grain can be expressed. Resolve this apparent circular dependency iteratively:

```text
Executive question
→ candidate outcome formula
→ candidate Factors
→ required business axes
→ candidate Dimensions
→ Factor natural grains
→ remove unused Dimensions and add missing ones
→ freeze the semantic contract
```

Every Dimension must serve at least one material Factor, Node view, approval policy, or executive question. Every Factor must have a defensible natural grain. Do not populate a theoretical cross-product merely because all Dimensions exist.

### Why this sequence became iterative

An early linear approach was to define Dimensions immediately after the expected outcome statement, then allocate totals across those Dimensions and design Factors afterward. That appeared practical because physical Factor configuration requires Dimensions. It proved unsuitable for logical design:

- Factors reveal which business axes are economically necessary.
- A Factor's natural grain can only be expressed using candidate Dimensions.
- Factors cannot be identified completely until the Node formulas are known.
- Detailed allocation cannot be governed until both the outcome formula and natural grains are stable.

Moving directly to the Factor-grain contract did not solve the problem either: it required both a stable Factor catalogue and stable Dimension codes. The corrected logical sequence is therefore:

```text
Independent expected Node totals
→ Node hierarchy and formula contract
→ candidate source and derived Factors
↔ candidate Dimensions and Factor natural grains
→ freeze Factor and Dimension semantics
→ Factor-grain and reusable Dimension-policy contracts
→ business events and approval intent
→ detailed Factor values
→ independently retained expected impacts
→ acceptance manifest
```

The double arrow is deliberate. Factor and Dimension design is a bounded iteration, not a one-way handoff. Freeze the pair only when every required formula input has a defensible grain and every proposed Dimension serves a material calculation, view, control, or decision.

This logical sequence must not be confused with system-entry order. Once design is frozen, physical configuration still creates Dimensions and members first, then Dimension policies, Factors and derivations, Nodes, and Analyses because those are the application's referential dependencies.

#### Example pivot record

| Decision field | Recorded learning |
| --- | --- |
| Initial approach | Expected totals → Dimensions → dimensional allocation → Factors and values |
| First change trigger | The Factors needed to answer the executive questions determined which Dimensions were necessary. |
| Intermediate approach | Expected totals → Factor-grain contract → Dimensions |
| Second change trigger | Factor grains could not be frozen before Node formulas identified the complete Factor set, or before candidate Dimension codes existed. |
| Confirmed approach | Expected totals → Node formulas → candidate Factors ↔ candidate Dimensions and grains → frozen contracts → events → values → impacts → acceptance |
| Implementation consequence | Maintain separate logical-design and physical-configuration sequences and preserve the crosswalk between them. |
| Validation | Every formula input maps to one Factor; every Factor has a defensible natural grain; every Dimension has a material use; no acceptance total is generated from the same detailed values it is meant to verify. |

## Distinguish calculations from dimensional slices

Define an economic calculation once and analyze it through governed Dimensions. Do not create separate Nodes for Country Revenue, Product Revenue, or Segment Revenue when these are filtered views of the same Revenue calculation.

For example:

```text
Node: Product Revenue
Filter: Business Unit = Commercial
```

Public or approved segment totals remain valuable acceptance anchors. Store them as a common target Node plus a governed Dimension filter, rather than creating a duplicate formula for each slice.

Separate Nodes remain appropriate when the economic formula or reporting basis genuinely changes—for example Segment Operating Profit, GAAP Operating Profit, and an organization-defined adjusted Operating Profit.

## Make recognition and timing explicit

For every operational flow, identify when the business event is measured:

- production;
- shipment;
- transfer of control or revenue recognition;
- sell-through;
- cash collection;
- period-end balance.

These are not interchangeable grains. A shipment may drive logistics expense and channel inventory while a recognition deferral delays Revenue. A current procurement-price increase may enter inventory now but affect Cost of Revenue only when the relevant inventory layer is released.

Record whether a Factor is a flow, a period-end balance, a rate, a compositional share, or a derived value. This prevents quantities and costs from being recognized in the wrong period or aggregated incorrectly.

### Do not manufacture a rate from an unstable snapshot

A rate numerator and denominator must describe the same measurement interval and economic exposure. Do not divide a quarterly flow by a beginning- or ending-period snapshot merely because those values are available. Likewise, do not add a beginning snapshot to all quarterly inflows and treat the result as if it were the amount continuously available throughout the quarter.

For example, channel inventory changes whenever units arrive or sell. `Beginning Inventory + Quarterly Shipments` is not a stable quarterly exposure base for a sell-through percentage because shipments arrive throughout the period. If daily or weekly inventory exposure is unavailable, prefer an independently planned quarterly Sell-Through flow and reconcile it through:

```text
Ending Inventory
= Beginning Inventory
+ Shipments
− Sell-Through
± governed inventory adjustments
```

If management needs a rate, define its denominator explicitly—for example average daily available inventory, average inventory, or a period-end weeks-of-supply measure—and collect the temporal data required to support it. Otherwise retain the flow and roll-forward and do not present a synthetic ratio as observed operational performance.

This is both a semantic and behavior decision: flows aggregate across time; snapshots select a point in time; and rates require a governed weight or exposure. A technically computable formula is not sufficient if its time basis is economically false.

A same-period flow ratio can, however, provide a valid governed simplification. If an outcome is controlled at a coarser grain than its operational source, first aggregate the source flow to that grain, calculate the controlled outcome, and derive an allocation ratio from two flows measured over the same interval. That ratio may then be expanded to detailed rows when the business explicitly accepts proportional allocation.

For example:

```text
Recognized Units at Country × Product
= Shipped Units aggregated to Country × Product
− signed Net Deferral Units

Recognition Ratio
= Recognized Units ÷ aggregated Shipped Units
```

Applying that ratio to detailed Customer or Route shipment rows preserves the governed total without broadcasting and duplicating additive units. Document the limitation: the detailed allocation is proportional and cannot support claims that recognition timing was observed at those finer Dimensions.

## Treat synthetic detail as a constrained model

When public or approved totals exist but operational detail does not, construct the detailed dataset as a constraint-satisfaction model. Do not generate plausible-looking rows independently and then hide the difference in a balancing Factor.

Use a source hierarchy:

1. audited filings or approved internal statements for outcome totals;
2. authoritative market trackers or official operational sources for external envelopes such as market volume and share;
3. management commentary for directional and timing constraints;
4. explicitly labelled synthetic assumptions for unpublished detail.

Preserve each source's definition, geography, period, and aggregation. A calendar-quarter market observation may be a useful proxy for an offset fiscal quarter, but it must be labelled as a proxy. A worldwide market total does not prove a Country split, and a directional market statement does not authorize an invented precise total.

Use at least three visible passes for a material synthetic model:

| Pass | Purpose | Required output |
| --- | --- | --- |
| Narrative construction | Encode the agreed business events and causal formulas | First complete Factor and Node result |
| Constraint calibration | Reconcile external market envelopes and independent outcome totals | Before/after values and the parameter family changed |
| Audit verification | Re-run without material adjustment and test Dimension rollups, impacts, composition, inventory, and uniqueness | Verification-only pass with no blocking variance |

If the first model reconciles financially but contradicts an external operating envelope, it has failed. Correct the causal surface before recalibrating prices, rates, or yields. Do not sacrifice market plausibility merely because the financial statement adds up.

Record public facts, proxies, synthetic hypotheses, and calculated values as separate evidence classes. For every synthetic allocation, retain:

- the public or approved envelope it must reconcile to;
- the business rationale for the allocation pattern;
- the Dimensions at which the allocation is synthetic;
- the permitted calibration parameter;
- the rejected alternatives;
- the final variance and tolerance.

For multiplicative or otherwise interacting models, retain exact Factor impacts only after source values are frozen. Dimension-member impact details must add to the global Factor impact. This allows Product, Country, Customer, channel, and other mix stories to be inspected without treating a change in revenue share as a standalone causal Factor.

Avoid a universal cross-product. Generate each Factor only at its natural grain and expand it through governed policies when consumed. Dataset size should follow economic applicability, not the total number of available Dimensions.

## Preserve a design decision trail

During discovery, record each consequential question using this structure:

| Field | Purpose |
| --- | --- |
| Decision ID | Stable reference for later implementation and agent use |
| Business question | The ambiguity that must be resolved |
| Recommendation | Consultant or agent proposal |
| Alternatives | Other valid interpretations and their trade-offs |
| Confirmed decision | Business expert's explicit choice |
| Rationale | Why the choice reflects the operating model |
| Affected objects | Nodes, Factors, Dimensions, policies, or acceptance controls |
| Previous design | The earlier assumption or implementation, including why it originally appeared reasonable |
| Change trigger | Evidence, worked example, or contradiction that exposed the need to reconsider it |
| Consequences | Objects to add, change, remove, retest, or document; include migration impact where relevant |
| Validation | The structural, numerical, workflow, and user-review evidence required after the change |
| Status | Proposed, confirmed, superseded, or deferred |

Do not rewrite history so that only the latest answer remains. Mark the earlier decision as superseded, link it to the replacement, and preserve why the team changed direction. A pivot is often more reusable than the final configuration because it records which plausible interpretation failed and what evidence distinguished the better design.

Update the decision trail immediately after each material design or test step—not only at workshop close. At minimum, update the working implementation journal and the relevant public-safe guide section while the reasoning is still fresh. The final acceptance record should point back to the decisions it validates.

This decision trail is part of the implementation evidence. A future agent should use it to ask precise follow-up questions, generate typed proposals, and explain why a configuration was recommended. It must not treat an unconfirmed interpretation as permission to create or activate master data.

## Discovery questionnaire

Complete these questions before creating configuration.

### Business scope

1. Which result or KPI will the Bridge explain?
2. Which two Version–Period workspaces will be compared?
3. Which future periods should be configured now so the model remains reusable?
4. Which dimensions and leaf members define the required investigation grain?

### Factor design

For every Factor, record:

- business definition and display Format;
- whether it is uploaded or derived;
- native source dimensions;
- behavior when dimensions are removed;
- permitted expansion across missing dimensions;
- derivation formula and dependencies;
- population method;
- contribution owner or Data Collation Group;
- Analysis Group required for analytical drill-down.

### Data and controls

1. Which columns identify Version, Period, Factor, and dimensions?
2. Are percentages supplied as decimals or percentage points?
3. How many native-grain facts should exist for each Factor and period?
4. Which group totals must reconcile, such as a mix summing to `1.0`?
5. What independently calculated reference total, current total, and variance will be used to accept the result?

## Acceptance plan

Define a control for every handoff:

- configuration: saved objects equal the approved design;
- Analysis: analytical Factors and supporting dependencies are complete;
- upload: accepted facts equal the native-grain expectation;
- finalization: derived results reproduce independent calculations;
- Bridge: current minus reference equals the displayed movement;
- BRRES: Factor Shapley values sum to the Bridge movement;
- audit: filtered detail and source lineage remain traceable.
